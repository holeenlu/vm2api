# tapmodels 需求交付与上游同步规范

适用于本项目的新增、修复、重构、撤销、上游同步及提交、推送。制定日期：2026-10-21。参考 sub2api 的需求归属、语义冲突审查和可复核交付方法，执行对象与授权以 tapmodels 为准。本文是交付流程的唯一详细规则；[AGENTS.md](../AGENTS.md) 保留协作入口与完整功能清理要求，业务契约由对应需求文档维护。

## 1. 分支、来源与交付目标

| 对象 | 当前用途 | 执行规则 |
| --- | --- | --- |
| `.github/workflows/upstream-sync.yml` | 每小时第 17/47 分钟、手动；只读预检与候选验证 | 不推送、不创建 PR、不发布镜像；报告和候选保留 14 天，见 [上游预检](UPSTREAM_SYNC.md) |
| 本地 `main` | tapmodels 定制主线 | 已授权变更在此交付；隔离任务可使用 `codex/<任务>` 工作分支 |
| `dofastted/vm2api` 的 `main` | 原项目上游，当前 remote 为 `origin` | 只读来源；保留原始上游历史；正式 main 只在冻结上游后接一个定制提交 |
| `holeenlu/vm2api` 的 `main` | 唯一默认代码交付分支，当前 remote 为 `vm2api_kdan` | `refs/heads/main:refs/heads/main`，推送前核对真实 fetch/push URL |
| 本地同名 `vm2api_kdan` 分支 | 既存本地引用 | 不因与 remote 同名成为第二交付分支，不自动移动、删除或发布 |
| 定制 sub2api 及其他参考项目 | 指定需求的设计、契约和实现参考 | 仅在本轮范围内按 tapmodels 架构选择性适配，不跨项目整分支合并 |
| `deploy/payload.json` 指向的上游资产 | 已锁定的内核、CLI 等二进制依赖 | 按文件来源、大小和 SHA256 验证；与代码推送仓库分别处理 |

remote 名称只是当前配置，必须每轮核验；不得因为名为 `origin` 就向其推送。允许使用同一目标仓库的正常 HTTPS/SSH URL，但需检查全部 push URL，以及 `url.*.insteadOf` / `pushInsteadOf` 等改写，确保没有额外目标。发现不一致时先解决目标身份，不能静默改 remote 或绕过核验。

本项目采用单主分支、单一定制提交交付。用户 2026-10-21 的最新要求取代此前“按功能拆分、归并原功能提交并保留本地 merge”的规则：`main = 最新冻结上游 + 一个包含全部定制差异的提交`。原作者的对象与祖先关系不改写，旧定制历史保存在仓库外 bundle；既有标签、Release 和其他任务引用保持。临时 merge 可以用于三方合并与语义审查，但不成为正式 main 的祖先。

当前需求从下表进入，再读取其中相关的最新修订与实际调用方。后续明确纠正优先于旧方案和旧验收数字；发现文档与实现不一致时核查来源，不自行把代码现状认定为新需求。

## 3. 授权与完成范围

- 制定规范、维护技能或只读审查不启动代码同步、提交、推送或发版。
- “同步上游”默认完成来源核验、工作区合并、冲突审查、清理与相关验证；提交、推送按用户本轮及已明确延续的授权执行。已经授权且目标明确的动作直接完成，不重复询问。
- 本机 Docker 验收、替换正在运行的容器、GitHub 构建验收、版本发布、外部部署和数据库处置分别遵守授权。代码发布不自动执行 `gh workflow run`、安装/升级脚本或数据库迁移。
- 改变明确业务需求、权限/安全边界或存在未决定的产品取舍时，先给出具体比较与推荐，再等待用户决定；纯机械冲突和已有明确决定直接处理。
- 部分来源不可达、测试失败或部署未执行必须分别说明，不把“已准备”“已验证”“已推送”“已发版”“已部署”混成一个完成状态。

## 4. 上游同步与选择性吸收

### 来源冻结与范围

未限定来源的 tapmodels 同步以 `dofastted/vm2api` 的 `main` 为上游。仅对本轮需要的来源 fetch，固定完整 SHA、本地基点、目标远端旧 SHA、共同祖先和先前已审查范围。抓取失败不等于没有更新；本地缓存引用也不能冒充本轮最新上游。实现过程中使用冻结的 SHA，不反复追逐移动中的远端分支。

用户指定 sub2api 或其他参考来源时，分别固定来源分支/SHA、功能边界和覆盖状态；本地未提交源码只能标为工作树快照并记录实际 diff，不能冒充远端提交。比较实际行为后区分应吸收、需补齐、已等效、排除及待决定项；相同修复只实现一次。保留源码出处、许可及署名；自包含补丁可用 `cherry-pick -x`，语义移植在提交说明或交付记录中注明来源 SHA/文件。

### 冲突决策

1. 对照 merge base、本地、上游的实现及调用链，同时检查文本冲突和自动合并后的跨文件行为冲突。优先检查权限、调度、重试、HTTP/SSE/WS、计费、数据归属、默认值、密钥持久化、资产来源和工作流副作用。
2. 对有实质取舍的功能，在解决前记录两侧的触发条件、正常/失败路径、需求来源、数据/配置影响和代码证据。比较采用上游、保留本地或融合的收益与损失，给出一个推荐；融合必须有单一规则归属，不能以并存旧路径或不断加开关代替决策。
3. 保护当前有效需求，不固守历史实现。上游完整满足需求时采用它并删除替代掉的本地实现；本地更适合时记录依据。改变明确需求的决定先展示给用户，得到答案后再修改依赖部分。不能用通过测试代替产品决定。
4. 无实质冲突时简述核查范围与结论即可。同一语义决定的文件可合并分析，独立选择分开处理；旧决定仅在输入与需求仍相同时复用。禁止整文件 `ours` / `theirs` 直接消除冲突。

### 执行与恢复

1. 在本任务干净隔离检出中，基于旧定制 main 对冻结上游执行 `git -c rerere.enabled=false merge --no-ff --no-commit <上游SHA>`，仅获得组合文件树。上游已包含时直接审查现有树，不创建空 merge。
2. 同时审查文本冲突和自动合并后的跨文件语义；保留本地有效契约，清理被替代实现。不能通过整个文件的 ours/theirs 消除业务选择，也不能因 Git 合并成功便省略权限、结算、协议和持久化核查。
3. 历史迁移保持；上游迁移与定制编号碰撞必须根据现有数据库契约另行解决并验证，不改写已应用迁移来隐藏冲突。数据处置遵循独立授权。
4. 用最终 index 的树生成唯一父提交为冻结上游的定制提交；提交正文包含当前完整 Release Note。旧定制提交、临时 merge 和逐次修补提交均不得作为最终提交的额外父提交。按第 6 节核验形状、备份、精确 lease 及本地收口。
5. 中断后恢复同一冻结输入、组合树、报告及验证，不追逐移动上游；相关源码或输入变化后重新验证受影响部分。不要改历史测试证据或 abort 别人的操作。

本轮私有证据放在 `.local/upstream-sync/<运行标识>/`（已由 `.gitignore` 忽略）。至少保留 `upstream-changes.md`：来源与旧新 SHA、审查范围、决策、最终树/提交、验证命令与结果、发布状态。复杂运行可另存结构化状态与日志；不要为简单任务创建空检查点框架。需随代码共享的交付摘要放在现有相关文档或明确的文档路径，剔除密钥、运行配置、数据库备份和私人日志。

## 6. 单一定制提交、推送与本地收口

### 每次交付必须满足

```text
… → dofastted/vm2api 最新冻结提交 → tapmodels 单一定制提交（main）
```

定制提交包含相对该上游的全部有效功能、需求、修复、品牌、测试、文档与交付工具。新增功能、跨功能调整、撤销、普通修复、同步上游均更新这个提交，不追加主题提交或正式 merge。提交正文使用完整 `docs/CUSTOMIZATION_RELEASE_NOTES.md`，不能只写本轮修补。至少逐项覆盖新增功能、优化改进、Bug 修复、破坏性变更、升级指南、清理/保留、已知限制和验证范围；没有某类变更时明确写“无”。

### 冻结与备份

1. 核验上游只读 URL、交付 fetch/push 的全部 URL 和 URL 改写。唯一代码发布目标为 `https://github.com/holeenlu/vm2api.git` 的 main。
2. 按顺序 fetch 上游 main、固定来源 SHA，再 fetch 交付 main、固定远端旧 SHA。审查远端其他修改后才形成候选，不自动刷新 lease 覆盖独立提交。
3. 记录主工作区、所有 worktree、暂存/未提交/未跟踪内容及旧引用。在仓库外创建并 `git bundle verify` 完整 bundle，保存旧 main、上游 SHA、最终树和新提交映射。新规则授权必要的定制历史重建；发版、生产部署和数据操作不因此获授权。

### 生成与验证

在已完成语义审查、清理和测试的 index 上，使用 `git write-tree` 取得组合树，再用 `git commit-tree <tree> -p <冻结上游SHA> -F <完整提交说明文件>` 生成单一定制提交。也可采用等效的隔离重建方法，但不能重写上游对象或把旧定制历史合回最终分支。未提交内容不得被隐式吸收。

必须核验：

- 新提交只有一个父提交，且等于本轮冻结上游。
- `git rev-list --count <冻结上游SHA>..<新提交>` 等于 1；上游本身既有的 merges 原样保留。
- 新提交文件树精确等于审查/验证的组合树。历史压缩不能复活撤销功能或漏掉任一原定制。
- `git diff <冻结上游SHA> <新提交>` 是累计定制说明的依据；`git diff <旧main> <新提交>` 是本轮代码变化与发布副作用检查依据，两者不能混用。
- 正式应用版本仍只允许人工发版。发版产生的版本快照提交只归 tag，不推回 main；既有 tag/Release 不为整理主线而移动或删除。

### 发布与收口

仅在已有代码推送授权下，对核验的目标 main 使用完整 refspec 和绑定旧 SHA 的精确 lease：

```bash
git push --force-with-lease=refs/heads/main:<冻结远端旧SHA> vm2api_kdan <已审查任务分支完整ref>:refs/heads/main
git ls-remote --heads vm2api_kdan refs/heads/main
```

不得使用裸 `--force`、裸 push、`--all`、`--mirror` 或标签批量推送。lease 失败时先保留并审核远端独立更新，再重新组合和验证；不能只刷新旧 SHA 重试。归并需要的非快进更新不等于发布应用版本或 guest/KVM 镜像。

保护其他任务后，把本地 main 收口到已交付提交并跟踪 `vm2api_kdan/main`，实时远端、本地 main、upstream 必须一致，ahead/behind 为 0/0。干净检出可使用受旧值保护的 read-tree/update-ref；有修改时先隔离保护，禁止默认 hard reset/stash。不要为消除分叉把旧 main merge 回单提交主线。

完成后把本任务引用和映射存入仓库外已验证 bundle，移除本任务干净的临时 worktree/分支。保留其他任务、来源不明的文件、旧用户分支和已发布标签；GUI 全分支视图仍可能显示被保留的历史，判断当前结构应查看 main 相对冻结上游的差异。

## 7. GitHub Actions、发版与部署边界

本项目当前工作流与 sub2api 不完全相同，不能一概写成“所有 Actions 只手动”：

| 工作流 | 当前触发及副作用 | 同步/交付要求 |
| --- | --- | --- |
| `.github/workflows/test.yml` | main push、PR、手动触发；质量检查 | 保留当前 CI，不能为照搬其他项目而关闭或伪称只手动 |
| `.github/workflows/release.yml` | 仅 `workflow_dispatch`；限 `holeenlu/vm2api` 的 main | 手动运行默认 publish=true，自动编号并发布；取消勾选仅构建验收；创建版本提交/tag、草稿、应用镜像及 Release 仍需相应调用授权 |
| `.github/workflows/guest-images.yml` | 先验证真实 before/after：非快进/forced 推送只记录跳过；正常快进且镜像输入变更才发布；也可手动 | 历史整理不发布镜像。需要发布新版 guest/KVM 时单独授权人工运行；读取失败、缺少旧提交或 checkout 不匹配时拒绝自动发布 |

GitHub 的 push paths 可能在历史重写时重新命中旧改动，不能只靠路径过滤判断安全。`guest_publish_guard.py` 对 forced/non-fast-forward 推送拒绝发布，普通快进还会检查实际旧、新文件树；不关闭普通 CI。涉及真实镜像内容变化仍需对应发布授权，不能偷偷删代码或停用工作流绕过边界。

应用版本及默认更新仓库保持 `holeenlu/vm2api`，tapmodels 控制面镜像使用 `ghcr.io/holeenlu/tapmodels-gateway`、linux/amd64，具体流程见 [品牌及发布](BRANDING_AND_RELEASE.md)。既存 ARM64 手动部署能力、guest 镜像来源与固定上游 payload 分别评估，不能误删、误改源或宣称已提供 ARM64 正式产物。推送不触发人工发版，不部署生产，不操作生产数据。

## 8. 交付报告
