# tapmodels 需求交付与上游同步规范

适用于本项目的新增、修复、重构、撤销、上游同步及提交、推送。制定日期：2026-10-21。参考 sub2api 的需求归属、语义冲突审查和可复核交付方法，执行对象与授权以 tapmodels 为准。本文是交付流程的唯一详细规则；[AGENTS.md](../AGENTS.md) 保留协作入口与完整功能清理要求，业务契约由对应需求文档维护。

本项目采用单主分支、单一定制提交交付。用户 2026-10-21 的最新要求取代此前“按功能拆分、归并原功能提交并保留本地 merge”的规则：`main = 已选定上游基线 + 一个包含全部定制差异的提交`。原作者的对象与祖先关系不改写，旧定制历史保存在仓库外 bundle；既有标签、Release 和其他任务引用保持。临时 merge 可以用于三方合并与语义审查，但不成为正式 main 的祖先。

## 3. 授权与完成范围

- **2026-10-22 持续代码交付授权：** 用户要求本项目功能修改完成、相关验证测试通过后自动提交并推送，不再逐次等待口头指令。适用于已授权的新增、修复、重构、撤销及对应文档；本次待交付 UI 修复一并处理。按第 6 节更新单一定制提交，推送唯一目标 `holeenlu/vm2api/main` 并收口本地 main。用户本轮明确限定只审查、不提交、不推送时优先遵守。
- 自动交付不省略相关验证、对应基线核验、独立远端变更审查、备份、树一致性与精确 lease。输入不变的成功验证可复用；未解决的冲突、失败或缺失的必要验证必须先处理，不能伪称通过或覆盖他人工作。只有确实需要用户作产品决定、提供信息或扩大授权时才请求输入。
- 普通推送产生的 CI 如实报告状态，无需等待全部远端任务结束才告知已推送；失败需定位处理。2026-10-28 起，上游新版本同步交付持续授权整套自动发布；同版本修改不自动发布。生产部署和数据处置继续单独授权。

- 制定规范、维护技能或只读审查不启动代码同步、提交、推送或发版。
- “同步上游”默认完成来源核验、工作区合并、冲突审查、清理与相关验证；提交、推送按上述持续授权及用户本轮限制执行。已经授权且目标明确的动作直接完成，不重复询问。
- 本机 Docker 验收、替换正在运行的容器、GitHub 构建验收、版本发布、外部部署和数据库处置分别遵守授权。代码交付只在同步上游新版本时触发第 7 节整套发布；不自动执行安装/升级脚本或数据库迁移。
- 改变明确业务需求、权限/安全边界或存在未决定的产品取舍时，先给出具体比较与推荐，再等待用户决定；纯机械冲突和已有明确决定直接处理。
- 部分来源不可达、测试失败或部署未执行必须分别说明，不把“已准备”“已验证”“已推送”“已发版”“已部署”混成一个完成状态。

### 普通需求与同步分流（2026-10-23 用户确认）

- 普通新增、修改、修复、撤销：基于当前已交付 main 开发，保持其唯一上游父提交；不查询/追赶最新上游，不把小修改扩为一次同步。只核对交付远端的独立变更，必要时融合后更新定制提交。
- 明确“同步上游”：读取实时上游，审查新增差异和冲突，交付前/收口前核验最新来源。无更新且无剩余变更则直接结束，不创建提交或重复推送。
- 只提交、归并或推送：接续已完成实现和有效验证，处理交付差异，不重走开发流程。明确只讨论或不提交时不发布。
- 当前工作区干净且没有并行任务占用时，普通需求可直接使用它；有无关修改或并行工作才隔离。上游合并继续在隔离检出进行。

## 4. 上游同步与选择性吸收

### 来源冻结与范围

未限定来源的 tapmodels 同步以 `dofastted/vm2api` 的 `main` 为上游。仅对本轮需要的来源 fetch，固定完整 SHA、本地基点、目标远端旧 SHA、共同祖先和先前已审查范围。抓取失败不等于没有更新；本地缓存引用也不能冒充本轮最新上游。每批合并与验证使用冻结 SHA；推送前及收口前核对实时上游，若前进则记录新批次并补入，只重跑受影响检查，最终父提交与最后核验一致。明确指定版本时遵守指定范围。

用户指定 sub2api 或其他参考来源时，分别固定来源分支/SHA、功能边界和覆盖状态；本地未提交源码只能标为工作树快照并记录实际 diff，不能冒充远端提交。比较实际行为后区分应吸收、需补齐、已等效、排除及待决定项；相同修复只实现一次。保留源码出处、许可及署名；自包含补丁可用 `cherry-pick -x`，语义移植在提交说明或交付记录中注明来源 SHA/文件。

### 网站 Changelog 与上游原文

每次同步必须从本轮冻结的上游 SHA 完整保存根目录 CHANGELOG.md，包含新条目、历史条目及上游对旧条目的修订。该文件由上游维护，不追加品牌说明、不改写原作者历史，也不因本地冲突而保留旧版；定制功能、迁移编号差异及定制修订说明统一写入 docs/CUSTOMIZATION_RELEASE_NOTES.md。CHANGELOG.md 是明确指定的文件归属例外，可按冻结上游整体恢复；其他文件仍执行下述语义冲突规则。

候选及最终提交须通过 `git diff --exit-code <冻结上游SHA> <候选或最终SHA> -- CHANGELOG.md`。上游文件缺失或不是普通受控文件时阻断并报告，不能静默继续使用旧日志。即使上游提交已包含，也要检查并修复该文件的本地偏差；baseline 预检只验证当前树，不修改日志。

网站 /settings/about 的 Changelog 由应用读取根目录 CHANGELOG.md；Dockerfile 已将它打包进应用镜像。核对日志随源码/镜像交付，网站在部署对应版本后更新；仅同步或推送 Git 不会更新运行中的网站，不能把 GitHub Release 的定制说明当作此页面的数据源。

### 冲突决策

**上游优先（2026-10-31 用户要求）：** 本轮涉及的功能重叠和冲突默认采用上游方案，使定制差异逐步收敛。两边等效且满足当前需求时也采用上游；“本地已有”“本地检查更严格”“本地测试已通过”都不能单独作为保留理由。本原则限定于本轮相关调用链，不要求每次重写全部定制。

1. 对照 merge base、本地、上游的实现及调用链，同时检查文本冲突和自动合并后的跨文件行为冲突。优先检查权限、调度、重试、HTTP/SSE/WS、计费、数据归属、默认值、密钥持久化、资产来源和工作流副作用。
2. 对有实质取舍的功能，在解决前记录两侧的触发条件、正常/失败路径、需求来源、数据/配置影响和代码证据。比较采用上游、保留本地或融合的收益与损失，给出一个推荐；融合必须有单一规则归属，不能以并存旧路径或不断加开关代替决策。
3. 上游满足当前需求时采用它，并同次清理被替代的本地实现、失效配置和测试；测试随真实接口调整，但保留仍有效的业务回归。例外仅限上游无法满足用户明确需求、已核实的权限/数据契约，或存在可复现回归；记录具体需求/调用方、失败证据、最小保留范围和移除条件。优先在上游实现上补最小必要差异，不长期并存两套路径。需要改变明确需求或安全边界且尚无授权时才请求用户决定；不能用修改测试掩盖需求丢失。
4. 无实质冲突时简述核查范围与结论即可。同一语义决定的文件可合并分析，独立选择分开处理；旧决定仅在输入与需求仍相同时复用。禁止整文件 `ours` / `theirs` 直接消除冲突。

### 已有能力的实现比较

已有实现只说明能力存在，不代表两边方案等效或本地方案更优。不能仅因名称相同、功能存在或已有测试通过，就标记“已覆盖”并跳过比较；也不能把同一能力再次整体移植，造成重复入口或长期并行的实现。

- **比较实际方案。** 对本轮涉及的同类能力，核对两边算法、数据结构、适用条件、输入输出契约、CPU/内存/延迟等开销，以及异常、取消、边界和资源限制处理。结合本项目调用链与负载判断，不能仅凭代码长短、项目来源或“更新”认定谁更好。
- **分别给出结论。** 对官方上游默认结论为“采用上游并清理替代代码”；确认等效后也收敛到上游，不能仅标记“本地已覆盖”就跳过。必要融合、保留本地或仅借鉴具体改进必须符合上述例外并给出证据；证据不足只补做影响决策的定向验证。非官方参考项目按用户指定范围比较，不自动获得官方上游优先级。改变已明确需求的取舍仍按冲突决策处理。
- **有必要才测性能。** 正确性先由相关契约/回归验证；性能优劣确实影响选择且现有证据不足时，才用相同环境、代表性输入和可比较参数做最小基准。区分源码推断与实测结果，不把待测结论写成已证实的优劣。输入及需求未变可复用既有比较，不每轮重审无变化实现。
- **例子用于定位，不自动扩大范围。** 出站 zstd 压缩应比较启用条件、压缩等级/流式策略、压缩收益、CPU/内存成本及失败处理；SSE 多行拼帧应比较跨 chunk/多 data 行的正确性、缓冲与拼接算法、帧大小限制、异常/截断和取消时的清理。若两边均有实现，先比较再决定保留或借鉴，不因提及这些能力就自动启动跨项目移植或全量基准。

### 执行与恢复

1. 在本任务干净隔离检出中，基于旧定制 main 对冻结上游执行 `git -c rerere.enabled=false merge --no-ff --no-commit <上游SHA>`，仅获得组合文件树。上游已包含时直接审查现有树，不创建空 merge。
2. 同时审查文本冲突和自动合并后的跨文件语义；保留本地有效契约，清理被替代实现。不能通过整个文件的 ours/theirs 消除业务选择，也不能因 Git 合并成功便省略权限、结算、协议和持久化核查。
3. 历史迁移保持；上游迁移与定制编号碰撞必须根据现有数据库契约另行解决并验证，不改写已应用迁移来隐藏冲突。数据处置遵循独立授权。
4. 用最终 index 的树生成唯一父提交为冻结上游的定制提交；提交正文包含当前完整 Release Note。旧定制提交、临时 merge 和逐次修补提交均不得作为最终提交的额外父提交。按第 6 节核验形状、备份、精确 lease 及本地收口。
5. 中断后恢复同一批次输入、组合树、报告及验证，再做交付前实时上游核验；相关源码或输入变化后重新验证受影响部分。不要改历史测试证据或 abort 别人的操作。

简单任务不新建空阶段报告；验证命令与结果可在一份交付记录简记。已有成功输出不重复摘录。

本轮私有证据放在 `.local/upstream-sync/<运行标识>/`（已由 `.gitignore` 忽略）。至少保留 `upstream-changes.md`：来源与旧新 SHA、审查范围、决策、最终树/提交、验证命令与结果、发布状态。复杂运行可另存结构化状态与日志；不要为简单任务创建空检查点框架。需随代码共享的交付摘要放在现有相关文档或明确的文档路径，剔除密钥、运行配置、数据库备份和私人日志。

## 5. 最小充分验证

先看实际行为和调用链影响，选能验证风险的最小组合；以下是选择规则，不是每次全部执行的清单。现有测试已覆盖时直接使用，不为每次可逆的小修改新增测试。新增测试应覆盖真实缺陷、边界或契约，不重复实现代码。

| 实际变更 | 本地默认验证 | 何时扩大 |
| --- | --- | --- |
| 文档、技能、注释、格式 | diff 检查；受影响引用或语法/格式检查 | 改可执行示例或流程语义时检查对应场景，不安装业务依赖 |
| 翻译、纯文案 | 资源可解析、占位符/键一致，相关现有 i18n 测试 | 修改渲染或加载机制才做类型/构建检查 |
| 样式、简单组件 | 修改文件格式/lint；会受影响的组件测试 | 可见布局/交互有变化时做一次针对性 UI 检查；不搭新 fixture 环境跑无关页面 |
| 前端逻辑、路由、状态 | 相关测试；类型、导入、组件接口或调用契约受影响时补类型检查 | 构建配置、依赖、入口、资源打包有变化才额外本地构建；build 已含 tsc，不先重复 typecheck |
| 后端功能或 Bug | 修改文件语法/格式与直接相关单测 | 改 HTTP/跨模块契约时补对应集成测试；不是所有后端修改都跑商业 E2E |
| 权限、账务、调度重试、协议流、持久化 | 对应回归，覆盖正常、拒绝/失败和本次边界 | 涉及跨层路径才加相应 E2E；共享基础层或影响不能确定才扩大到模块/全量 |
| SQL、Schema、迁移 | 隔离的真实数据库升级与相关查询回归，检查已有数据、约束及幂等 | 不用 mock 替代真实迁移；没有持久化变化不启动数据库专项，不触碰生产库 |
| Go 模块 | 修改包及受影响调用方测试和格式；并发相关使用定向 race | 跨包公共能力/依赖变化才扩大至该模块全量、vet 和编译，不自动重跑另一个模块 |
| 构建、依赖、payload、工作流、发布保护 | 对应现有工具/契约测试与必要构建 | 输入未知或影响广泛才全量；Linux 专属检查交已有 CI，不在 macOS 反复排障 |
| 只归并提交/推送，代码未变 | 树、说明、来源/目标、备份与 lease 核对 | 不因 SHA、提交正文、统计文档变化重跑业务检查 |

扩大到模块/全量前，明确说明受影响共享调用链，或无法可靠限定范围的具体原因；不能仅凭“鉴权、计费、网关”目录名升级全量。定向测试仍覆盖入口、失败路径和受影响调用方。

只跑缺失或被最终修改影响的检查。全量检查、浏览器、Docker、真实供应商和付费推理不属于默认步骤；后几项仍遵守各自授权。根 npm test 不包含全部前端/内核/E2E，不能用它概括所有验证。

本地负责快速反馈与冲突/高风险回归，CI 负责选中范围的标准环境检查；不在两边主动重复完整矩阵。每条命令覆盖什么写清楚，成功结果按相关源码、依赖、生成输入、命令及工具链/环境等效复用。格式化后无语义变化只重验格式；测试失败修复后只重跑受影响项；不因更换提交 SHA 重新从头验证。

测试已覆盖同一编译条件时，不再额外普通构建或重复同类分析；CGO、build tags、生成资源、入口打包与发布参数不同则属于不同验证，仍需相应检查。读取状态和计算差异批量进行，已有证据只引用，不为交付反复编排相同脚本。

优先复用匹配版本的已安装工具及共享缓存。不要把其他正在收尾任务的 node_modules 当成本任务可靠依赖目录；避免其删除造成断链。没有必要验证时不安装依赖。简短证据记录命令、输入和结果即可，已有工具记录不再手抄大量日志或生成空检查框架。

### 同步效率与中断恢复

更新日期：2026-10-23。

按以下阶段推进，每个阶段完成后只因相关输入变化而回到受影响阶段。流程维护只维护当前流程，不额外启动业务同步；恢复任务以真实 refs 和文件树为准，不以旧对话摘要判定未完成。

| 阶段 | 执行动作 | 进入下一阶段的条件 |
| --- | --- | --- |
| 核对现状 | 批量核对来源、交付 main、工作区、未完成操作及本任务证据；已交付等效内容直接复用 | 有唯一实际基点和明确剩余工作；无新增内容不空合并、不空提交 |
| 确定增量 | 旧上游到新上游、本地定制交集及相关调用链；匹配的预检候选/证据可复用 | 本轮影响范围与契约明确；只建或复用一个任务检出 |
| 处理冲突 | 默认采用上游；等效功能收敛，必要例外保留最小差异；自动合并也查跨文件语义 | 冲突已解决；替代实现已清理；例外有需求/证据及移除条件 |
| 相关验证 | 先列相关检查、有效证据、环境限制；只跑缺失/受影响项 | 必要本地检查通过，Linux 检查的实际状态清楚 |
| 单次交付 | 修正累计说明与索引、备份、核验新树/唯一父提交/最新源，再精确 lease 推送 | 本地 main 与远端一致；CI 状态独立报告 |
| 清理收口 | 已验证归档覆盖任务提交和遗留草稿，再移除本任务临时分支/检出及可重建输出 | 本任务不遗留临时分支/检出；其他任务不受影响 |

**避免重复合并。** 同一次交付只有一个执行者负责最终 ref 更新；其他任务已在处理相同基点/来源时，先核对可用产物，推进独立部分，不再复制一轮合并。协调不替代精确 lease，也不自动授权向其他聊天发消息。其他任务已经交付后，保留其成果，只处理真实剩余差异，不回放旧草稿。

**限定审查范围。** 使用 contracts.json 定位当前变更影响的需求与测试。完整累计差异用于防遗漏，不要求每次重新逐行审查全部定制。累计说明保留仍准确内容，只修订实际变化。TTL 等跨文件修改沿定义、参数、调用方和默认行为验证；权限、账务和持久化等受影响时扩大审查，不能机械保留旧实现或依靠编译通过作决定。

**一次规划验证。** 本地执行相关格式、语法、单测及高风险回归，Linux 矩阵由已有 CI 执行。复用证据须确认相关源码、依赖、生成输入、命令、工具链和环境相同；仅 SHA 或交付阶段变化不作废。文档/技能不跑业务构建，格式修改只验格式，未改 UI 不启动浏览器。已确认的平台限制停止重复探测，标注等待相应 CI；真实失败修复后重跑受影响项。同一环境失败无新证据不重试，不反复冷装依赖。

**同步任务的最新上游不等于重新开始。** 仅同步任务在推送前与完成前核验最新来源；若有新提交，只整合新增批次、刷新受影响说明并补测。已审查决定和无变化输入的结果继续有效。目标远端前进时先保留独立修改，再计算新差异与 lease，不重新覆盖一整棵旧草稿树。

**CI 内部范围。** 仅 Node 单测变化时运行仍存在的变动测试文件；删除测试则回退 Node 全量。已审查的 image-edit-multipart 解析模块运行解析及 Images 入口两组单测与商业 contracts，其生产调用方发生变化则回退；其他后端边界未枚举时仍运行 Node 全量和 contracts，不假定任意动态调用都已分析。工作流/部署/发布 Python 回归只在工具输入变化、未知输入回退或手动/预检全量时运行，panel-users/onboarding 单测不在全量 suite 外重复执行。

仅 Go 测试文件变动时只执行该包测试，不带 Node/HTTP 集成或额外命令构建。Go 源码变动仅处理变动模块，以 go list 的生产依赖、测试导入与外部测试导入选择受影响包及传递调用方，所选包执行 race。模块依赖/资源变化、删除或受构建条件影响无法定位的包、依赖解析失败则回退该模块全量；未知范围和手动/预检验证两个模块。不重复额外全量 vet；go test 自带默认 vet。受影响命令的 CGO_ENABLED=0 构建与 race 编译条件不同，继续保留。现有 Python 选择器同时执行明确 argv，不拼接待测路径为 shell 指令。

**保留 CI，减少等待中的空转。** 普通 push/PR 比较真实前后树，不能用 HEAD^ 代表重写前交付。文档跳过业务；web 跑前端；Node 跑 unit/contracts；仅 unit 测试改动只跑 unit；Go 跑 worker/unit/contracts；工作流、依赖、payload、未知范围或缺失基点跑全量。预检/手动保持全量，result 汇总防止意外跳过。保留预检的无更新跳过和相同输入去重。CI 排队不触发反复本地全测、重复提交或重复请求授权；失败仍需定位处理。报告区分“代码已交付”和“CI 已通过”。

**有依据地报告耗时。** 用现有命令/运行时间报告阶段与瓶颈；可交付阶段超过五分钟需说明实际耗时及剩余项。2–5 分钟只能作为简单交付的优化目标，不保证复杂冲突的完成时间，不增加计时系统或为赶时间省略必要检查。

## 6. 单一定制提交、推送与本地收口

### 每次交付必须满足

同步任务选择最新上游；普通需求保持当前已同步基线。以下“冻结上游”均指本轮选定基线，只有同步任务需追赶实时来源。

```text
… → dofastted/vm2api 选定基线 → tapmodels 单一定制提交（main）
```

定制提交包含相对该上游的全部有效功能、需求、修复、品牌、测试、文档与交付工具。新增功能、跨功能调整、撤销、普通修复、同步上游均更新这个提交，不追加主题提交或正式 merge。提交正文使用完整 `docs/CUSTOMIZATION_RELEASE_NOTES.md`，不能只写本轮修补。至少逐项覆盖新增功能、优化改进、Bug 修复、破坏性变更、升级指南、清理/保留、已知限制和验证范围；没有某类变更时明确写“无”。

### 冻结与备份

1. 核验上游只读 URL、交付 fetch/push 的全部 URL 和 URL 改写。唯一代码发布目标为 `https://github.com/holeenlu/vm2api.git` 的 main。
2. 同步任务按顺序 fetch 上游 main、固定来源 SHA，再 fetch 交付 main、固定远端旧 SHA。普通需求沿用已交付 main 的唯一上游父提交，只读取交付目标；确认基线原始对象和既有交付记录，不追赶上游。两者都先审查远端其他修改，不自动刷新 lease 覆盖独立提交。
3. 记录主工作区、所有 worktree、暂存/未提交/未跟踪内容及旧引用。在仓库外创建并 `git bundle verify` 完整 bundle，保存旧 main、上游 SHA、最终树和新提交映射。新规则授权必要的定制历史重建；上游新版交付按第 7 节发布；其他发版、生产部署和数据操作不因此获授权。

### 生成与验证

在已完成语义审查、清理和测试的 index 上，使用 `git write-tree` 取得组合树，再用 `git commit-tree <tree> -p <冻结上游SHA> -F <完整提交说明文件>` 生成单一定制提交。也可采用等效的隔离重建方法，但不能重写上游对象或把旧定制历史合回最终分支。未提交内容不得被隐式吸收。

必须核验：

- 新提交只有一个父提交，且等于本轮冻结上游。
- `git rev-list --count <冻结上游SHA>..<新提交>` 等于 1；上游本身既有的 merges 原样保留。
- 新提交文件树精确等于审查/验证的组合树。历史压缩不能复活撤销功能或漏掉任一原定制。
- `git diff <冻结上游SHA> <新提交>` 是累计定制说明的依据；`git diff <旧main> <新提交>` 是本轮代码变化与发布副作用检查依据，两者不能混用。
- 提交生成及推送前，复核本轮涉及的累计差异是否仍有上游已等效满足的本地实现；确认已清理替代路径。Release Note 和提交正文逐项记录采用上游、必要融合或例外保留，例外注明需求/证据、最小范围及移除条件；不能以“保留全部定制”恢复已被上游替代的代码。沿用单一定制提交、备份、树一致性与精确 lease，不扩大授权。
- 上游新版同步后自动按原版号发版，tag 直接指向已交付定制提交；显式人工修订版的版本快照只归 tag，不推回 main。既有 tag/Release 不为整理主线而移动或删除。

### 发布与收口

仅在已有代码推送授权下，对核验的目标 main 使用完整 refspec 和绑定旧 SHA 的精确 lease：

```bash
git push --force-with-lease=refs/heads/main:<冻结远端旧SHA> origin <已审查任务分支完整ref>:refs/heads/main
git ls-remote --heads origin refs/heads/main
```

不得使用裸 `--force`、裸 push、`--all`、`--mirror` 或标签批量推送。lease 失败时先保留并审核远端独立更新，再重新组合和验证；不能只刷新旧 SHA 重试。非快进/forced 本身不决定发版；仅实际集成的上游版本递增时触发整套发布。

保护其他任务后，把本地 main 收口到已交付提交并跟踪 `origin/main`，实时 `upstream/main`、本地 main、`origin/main` 的关系必须明确，交付远端与本地 main 应为 0/0。干净检出可使用受旧值保护的 read-tree/update-ref；有修改时先隔离保护，禁止默认 hard reset/stash。不要为消除分叉把旧 main merge 回单提交主线。

完成后把本任务引用和映射存入仓库外已验证 bundle，移除本任务临时 worktree/分支，清理是完成条件而非后续可选动作。本任务被替代的脏草稿先完整归档源码、有效未跟踪文件、index/merge 状态及必要忽略配置并校验；可重建的 node_modules/dist/cache 不归档。确认归属、无他人占用和可恢复后再删除，不能因存在未提交内容而无限保留。仅有 bundle 不代表未提交草稿已经备份。保留其他任务、来源不明的文件、旧用户分支和已发布标签；GUI 全分支视图仍可能显示被保留的历史，判断当前结构应查看 main 相对冻结上游的差异。

## 7. GitHub Actions、发版与部署边界

本项目当前工作流与 sub2api 不完全相同，不能一概写成“所有 Actions 只手动”：

| 工作流 | 当前触发及副作用 | 同步/交付要求 |
| --- | --- | --- |
| `.github/workflows/test.yml` | main push、PR、手动触发；质量检查 | 保留当前 CI，不能为照搬其他项目而关闭或伪称只手动 |
| `.github/workflows/release.yml` | main push 与 `workflow_dispatch`；限 `holeenlu/vm2api/main` | push 仅在实际 before/after 的上游 VERSION 递增、源码继承该上游版本且基线核验通过时，按原始 X.Y.Z 自动发布应用与全部 guest/KVM。人工运行保留 X.Y.Z.N 修订（新基线从 N=1 开始，后续最大已占用修订号加 1）及 publish=false 构建验收；手工定制版默认复用 guest/KVM，槽位源码变化或 `rebuild_guest_images=true` 时才重建 |
| `.github/workflows/guest-images.yml` | 由系统发版通过 `workflow_call` 调用，也可显式人工运行 | 每次上游新版整套发布均构建全部 4 个 guest 和 4 个 KVM 镜像，即使镜像目录未变；冻结同一源码，任一失败阻止最终应用 Release 公开。无独立 push 路径触发 |
| `.github/workflows/actions-retention.yml` | 现有各工作流完成后、每小时第 31 分钟、手动；跨 All workflows 合计保留最新 10 条 | 按创建时间与 run id 排序，保留最新 10 条及仍运行的较旧记录；删除更旧已完成 run 及其日志/产物，不删除 Release、标签、镜像或代码。清理自身不触发自身；新增工作流时更新完成触发名单，定时补查仍覆盖全仓 |

`upstream_release_guard.py` 比较真实推送前后 VERSION 和唯一上游父提交，允许已核验的新版本历史重写；同版本修改、归并、仅镜像输入变化、回退均不自动发布。旧提交不在 checkout 历史中时按事件 SHA 定向读取，读取失败或 checkout 不匹配即失败关闭。自动规划核验冻结父提交属于官方上游 main 历史且源码版本一致，不因上游再次前进而误标新版本；人工修订使用当前发布源码的唯一上游父提交及其 VERSION，核验其属于官方 main 历史，不要求追赶最新上游；已正式发布的同名版本跳过，失败草稿仅允许原源码重试，不覆盖其他源码 tag。应用镜像完成检查、烟测和推送，全部 guest/KVM 成功后，才公开 Release 和提升应用 latest。普通 CI 保留，不以 CI 推送替代部署。

应用版本及默认更新仓库保持 `holeenlu/vm2api`，tapmodels 控制面镜像使用 `ghcr.io/holeenlu/tapmodels-gateway`、linux/amd64，具体流程见 [品牌及发布](BRANDING_AND_RELEASE.md)。既存 ARM64 手动部署能力、guest 镜像来源与固定上游 payload 分别评估，不能误删、误改源或宣称已提供 ARM64 正式产物。同步上游新版的推送触发整套发版，同版本修改不发版；不部署生产，不操作生产数据。

## 8. 交付报告

报告规模与任务匹配，至少给出可核对的结果：

- 实际范围、来源仓库/分支/冻结 SHA、审查区间；选择性吸收逐项说明采用、等效、排除或未完成。
- 累计 Release Note 必须完整覆盖新增功能、优化改进、Bug 修复、破坏性变更、升级指南（无内容的类别写明“无”）；界面写真实导航和路径，配置写实际字段及默认值，区分新装默认、已保存值、内部常量与迁移行为。无需配置的修复可写“部署后自动生效”，同时明确是否真的部署。
- 采用的冲突决定、删除/恢复/有依据保留的路径；仍需独立处理的数据与限制。
- 本轮实际验证命令、结果、输入提交或树、环境及未覆盖项；历史报告不作为本轮通过凭据。
- 本地提交、远端目标/实测 SHA、主工作区状态；未授权的提交/推送/发版/部署分别说明。
- 分开报告相对旧 main 的本轮差异和相对冻结上游的累计定制差异；按各自差异统计业务代码、测试的新增/删除/净变化，包含未跟踪新文件；文档与技能单列，原有无关差异剔除。报告新增接口、配置项、执行路径数量，恢复原逻辑与新增功能明确区分。

技能入口为本机 `$vm2api-sync-upstream`（`~/.codex/skills/vm2api-sync-upstream/SKILL.md`）；它提供上述制度的执行步骤，不替代本文，也不调用 sub2api 的 checkpoint、品牌传播或发布脚本。

产品品牌为 tapmodels，部署只面向全新环境；保留的 vm2api 仓库、remote、本机技能名称和上游来源是实际标识，不是旧部署兼容逻辑。品牌及部署契约见 [品牌与发布](BRANDING_AND_RELEASE.md#tapmodels-全新部署契约2026-10-21)。
