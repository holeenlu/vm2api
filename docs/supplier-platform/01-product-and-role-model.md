# 产品与角色模型

更新于 2026-10-30。当前实现和未实现目标分别见 [复核矩阵](11-system-review-20261030.md)。本页长期目标不代表接口已实现。

## 1. 产品边界

供应商平台是模型网关的资源供给和运营层。它管理供应商持有的上游账号、代理、授权、分组供给、用量和合同结算；终端用户通过平台分配的能力使用模型；平台管理人员负责授权、风控、资源调度和对账。

供应商平台不把供应商凭据提升为平台管理员凭据，也不允许供应商通过共用接口访问其他供应商的完整资料。供应商门户可以是独立前端镜像，但只调用同一个后端业务 API，数据库和 Redis 凭据只由后端持有。

## 2. 身份、主体与资源分层

| 层 | 对象 | 说明 |
|---|---|---|
| 身份层 | `super_admin`、`admin`、`user`、`vendor` | 登录主体和授权起点；供应商层级不拆成登录角色 |
| 组织层 | 平台、一级供应商、二级供应商 | 供应商形成最多两层树；二级必须有一级父级和根节点 |
| 资源层 | 上游账号、授权、代理、分组、VM、模型 Key | 资源有明确 owner；共享资源必须有显式供给授权 |
| 交易层 | 合同、用量快照、结算单、付款流水、调整单 | 平台→一级与一级→二级分开计量、确认、支付和冲正 |
| 证据层 | 审计事件、权限变更、导出记录、撤销记录 | 敏感操作和范围裁剪必须可追溯 |

## 3. 角色定义

### 3.1 超级管理员 `super_admin`

平台最高治理角色，负责：

- 创建、停用和恢复一级供应商；
- 创建、删除、重建、导入、分配和调度平台 VM；
- 管理平台级角色策略、能力目录、供应商准入和合同模板；
- 查看平台聚合用量、直属供应商用量和结算全链路；
- 处理身份 reconciliation、敏感导出、争议和平台侧付款；
- 授予或撤销管理员的模块、动作、字段和用户范围。

超级管理员不等于绕过审计。敏感读取、凭据导出、合同调整和付款的 step-up 属于尚未落地的目标；当前仅有已有会话认证、动作权限、理由和业务审计，不得宣称已实现 step-up。超级管理员个人账户的余额豁免如果存在，也只影响个人余额 admission/deduction，不豁免 Key、窗口、平台配额和供应商结算。

### 3.2 管理员 `admin`

管理员按现行管理域管理同域用户/管理员，可以创建下级管理员和普通用户，并查看本域消费数据；不能管理超级管理员或供应商。它不能创建或管理 VM、账号、代理、平台模型、系统设置或供应商。

未来如果需要给管理员角色增加其他能力，仍必须通过超级管理员委派的 `subject_scope`、`resource_scope`、`actions`、`fields` 和有效期控制；当前规划不授予供应商管理权限。

### 3.3 用户 `user`

终端用户，默认只拥有自己的：

- 模型 API Key；
- 被分配资源的使用投影，不拥有 VM 创建和生命周期管理权；
- 请求日志、统计、用量和个人账单；
- 自己创建的 Key 的生命周期操作。

用户不能创建或管理 VM、代理、平台池、供应商上游账号、合同或其他用户的密钥。`vm2api` 当前 `resource-owner` 的 owner/origin 规则继续用于服务端过滤，但 VM 创建和生命周期权限只保留给 SA。

### 3.4 供应商 `vendor`

供应商是唯一的供应商登录角色。登录用户绑定一个供应商主体，供应商主体通过 `tier/parent_id/root_id` 表示一级或二级层级，并单独保存状态、能力和额度策略。

| 供应商层级 | 能管理的对象 | 默认能力 |
|---|---|---|
| `tier=1` | 创建和管理自己的服务提供商账号、VM、代理，查看自己的用量；可按能力查看直属二级供应商聚合 | `vendor.resource.manage`、`vendor.vm.create`、`vendor.usage.read`；是否能创建下级由 `vendor.create_child` 决定 |
| `tier=2` | 创建和管理自己的服务提供商账号、VM、代理，查看自己的用量和结算资料 | `vendor.resource.manage`、`vendor.vm.create`、`vendor.usage.read`；系统不授予继续创建下级的能力 |

供应商可以拥有或被授予下列能力，但能力与层级分开判断：

- `vendor.create_child`：允许一级供应商创建直属二级供应商；
- `vendor.resource.manage`：管理自己的账号、代理、授权、暂停和归档；
- `vendor.resource.export`：预留导出能力，尚未提供导出/step-up 流程；
- `vendor.usage.read`：读取自己范围的汇总和明细投影；
- `vendor.settlement.read` 控制结算读取；`vendor.settlement.pay` 由超管显式授予一级，控制自己的下游确认/付款登记/作废；`vendor.settlement.confirm` 为收款确认预留，尚未实现。

## 4. 供应商层级规则

供应商树最多两层：平台 → 一级 → 二级。供应商状态必须为 `active` 才能访问业务资源；父级停用时，直属子级的业务写入和新请求资格同时失效，但历史读取按产品策略保留只读窗口。

允许创建下级供应商必须同时满足：

1. 当前身份是有效的 `vendor`，且当前供应商 `tier=1`；
2. 当前供应商拥有 `vendor.create_child`；
3. 父级状态为 `active`，且没有超过 `child_limit`；`child_limit=0` 表示不限制直属下级数量；
4. 新供应商的 `tier=2`、`parent_id=当前供应商.id`、`root_id=当前供应商.id`；
5. 新供应商的 groups、platforms、account_limit、proxy_limit 都是父级允许范围的子集，额度不超过父级；
6. 必须创建独立登录账号，不能绑定任意已有 user_id；邮箱、用户名和供应商外部编码在有效记录中唯一；
7. 创建和能力授予写入同一事务，并产生审计事件。

禁止通过接口参数创建三级节点、改变 root、绕过父级集合约束或借用其他树的资源。

## 5. 参考版 `sub2api` 的保留点

- `super_admin/admin/user/vendor` 是登录角色，供应商 `tier=1/2` 是组织属性；
- 供应商实体带 `tier/parentId/rootId/status`，有效性递归检查父级；
- 一级管理二级只限直属关系；资源读写和结算读取分别判定；
- 价格、倍率、汇率和合同按消费发生时间选取，旧账冻结合同版本；
- 供应商门户只是前端与反向代理，真实鉴权仍在后端；
- API 注册表、页面导航和权限策略分开维护，注册存在不代表任何角色都能调用。
