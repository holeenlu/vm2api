# tapmodels 中转站运营体系整合规划

2026-10-28 权限修订：SA/AD/U 当前职责以 [菜单与角色规划](supplier-platform/09-menu-and-role-plan.md) 和 [面板 API](PANEL_API.md) 为准。下文的旧站长/运维分工属于历史设计；现由 SA 独占资源运维，AD 仅管理普通 U 并读取 U 使用数据，商业分组/资金/套餐能力继续保留。

版本：2026-10-20。本文保留实施前的架构评估和约定；当前实现、清理范围、本机部署与实测结果见 [交付验收报告](RELAY_OPERATIONS_DELIVERY.md)。未执行外部生产部署或生产数据库迁移。

## 1. 目标、范围与实施位置

目标是在 tapmodels 内形成与用户当前定制 sub2api 对齐的运营体系：站长维护供给与商品分组、管理用户和资金；运维维护 VM／上游账号与运行状态；客户选择获授权分组、创建 API Key、调用服务并查看本人消费。

用户在本轮明确补充：VM 当前“分配给租户”改为“分配给分组”。这是一项资源关系变更，覆盖卡片菜单、详情弹窗、完整详情页、列表分组列、多选对话框、后端关联和调度授权，不能仅替换按钮文字。

本方案以 tapmodels 为实施仓库：保留 Node 控制面、React 控制台、SQLite 和现有槽位执行机制，引入定制 sub2api 的业务契约及页面能力。没有把“整合”解释成跨仓库合并，也不要求同时部署两个收费入口。若目标另行改为由现有 sub2api 实例直接运营，见第 15 节的替代拓扑；两种拓扑不得混用账本。

## 2. 现状评估：哪些能复用，哪些还不是运营能力

| 领域 | 当前已核实实现 | 与目标的差距 / 处理 |
| --- | --- | --- |
| VM 资源 | 槽位、Docker/KVM、节点、出口、凭证、调度、5h/7d 窗口、测试、终端 | 保留；增加所属分组、组内可用状态与按组调度范围 |
| 身份 | admin / super / user，面板会话与协议 Key 分开 | user 当前是资源租户，需转为 API 客户；super 默认仅有限查看和调度，需扩展运维能力 |
| users | 已有 balance、concurrency、status 等字段 | 当前用户页面/创建更新流程主要暴露身份和自建 VM 配额；需接入余额、商业额度、分组授权和审计 |
| groups | coding / other 两个固定行，主要提供计费倍率 | 尚不承载完整商品分组 CRUD、用户资格、模型和资源分配 |
| VM 资源池 | vm_pools 与 vm_pool_members；一台 VM 只能属于一个池；Key 可绑定池 | 与“一台 VM 可属于多个商业分组”不等价；需要迁移，不可把 pool_id 改名成 group_id 后继续双轨运行 |
| 资源所有权 | 用户 Key 默认只调度 owner_user_id 为本人者 | 不适用于客户共享平台供给；改为分组授权与资源归属分离 |
| 账号标识 | accountIdOf 优先取槽凭证 account_uuid，后备 vm.id | 分组必须能分配尚未绑定凭证的空槽，不能只依赖上游账号 UUID |
| API 地址 | api_endpoints、ApiScheduler 和 api-kernel 为另一条现有推理分支 | 分组、余额与计费必须覆盖这条分支；不能只保护 VM 路径 |
| Key | 已有状态、过期、并发、RPM、金额/次数、5h/1d/7d 窗口 | 复用 Key 生命周期；范围改为获授权商业分组，客户不选择内部 VM/池 |
| 钱包 | 余额字段、追加流水、管理员转账和请求预留已形成闭环 | 充值只允许管理员从本人可用余额转给普通用户；兑换码入口已移除，历史表仅保留数据兼容 |
| 使用记录 | usage_logs、request_attempts、统计、明细、导出已存在 | 当前 ownerPred 还会按当前 Key 属主或历史 VM 属主扩展可见行；客户记录需按调用用户快照归属 |
| 费用 | total_cost / actual_cost、倍率快照、模型计价已有基础 | 财务结算、上游账号统计成本与客户实扣必须分清；不得把官方价直接当采购成本 |
| 运维 | overview、VM、cluster、risk、数据库指标、日志诊断、SSE | 整合为独立运维视图，参考定制 sub2api 的错误分类、SLA、任务和调度轨迹能力 |

源码证据见第 16 节。上表是实际调用链核对，不以字段或表已经存在认定功能已经完整。

## 3. 目标业务模型

### 3.1 对象关系

~~~mermaid
flowchart LR
    Staff[站长与运维] --> VM[VM 槽位与上游账号]
    Staff --> EP[已有 API 地址资源]
    VM --> GR[分组资源关联]
    EP --> GR
    GR --> G[商业分组：模型、价格、售卖规则]
    G --> UG[用户分组授权或订阅]
    U[客户] --> UG
    U --> K[客户 API Key]
    K --> G
    U --> W[用户余额或套餐权益]
    K --> A[统一准入与调度范围]
    W --> A
    A --> R[现有 VM / API 推理链]
    R --> S[实际用量与一次结算]
    S --> W
    S --> L[客户使用记录]
    R --> O[运维尝试与诊断]
~~~

- 一个客户可获授权多个分组；一把新建客户 Key 绑定一个商业分组。
- 一个分组可关联多个 VM；一个 VM 可以关联多个分组。不同分组共享同一个 VM 的真实并发、席位与上游额度，不能按分组复制容量。
- VM 和代理由平台管理。客户的分组调用资格不产生 VM 管理权，也不产生查看上游凭证的权利。
- VM 的 vm.id 是稳定的资源关联标识；实际执行账号 account_id 作为请求时快照记录。空槽可提前分组，只有凭证、出口和运行条件满足后才进入可用候选。
- 一个客户的全部 Key 共享用户资金与用户级限额；Key 限额只是进一步收紧，不能充值或重置用户商业权益。
- 使用记录属于请求发起者；运维资源归属、执行资源和结算对象分别保存，不能互相替代。

### 3.2 sub2api 对象在 tapmodels 的对应

| 定制 sub2api | tapmodels 目标对象 | 采用方式 |
| --- | --- | --- |
| Account | VM + 实际上游账号 + runtime | UI 承担“账号资源”职责；保留 VM 特有的节点、镜像、内存、种子、终端与隔离出口 |
| Account.group_ids | VM 的 group_ids / groups 摘要 | 新增多对多关联；VM 列表、详情和批量编辑显示多个分组 |
| Group | 扩展现有 groups | 商业商品/服务规则的唯一实体；不再同时向用户暴露 coding/other 与账号池两套选择 |
| User / allowed_groups | 现有 users + 用户分组授权 | 账户状态、资金、并发、公开组访问规则、专属组授权及用户组倍率 |
| ApiKey.group_id | 现有 api_keys.group_id | 创建、修改和调用时都校验授权，用户请求不能修改 user_id 或财务字段 |
| UsageLog / Ops errors | usage_logs + request_attempts / 诊断 | 共用请求标识；客户消费和运维排障具有不同字段投影 |
| balance / subscription | 用户钱包、资金流水、用户订阅 | 手工充值与消费先形成完整闭环；套餐接入同一结算服务 |
| admin_role_policy | 扩展 panel-acl 的能力与字段授权 | 保留 tapmodels 角色名；消费权限快照，避免前后端各自推断角色能力 |

特别注意：tapmodels 的 admin 对应站长职责，super 对应受限运维；不能把 super 按字符串对应成 sub2api 的 super_admin。

## 4. 商业分组设计

### 4.1 分组字段与页面能力

| 字段区 | 目标能力 |
| --- | --- |
| 基本信息 | 名称、说明、排序、启停、公开/专属、支持平台；普通组限于当前实际支持的 Claude/Codex 或明确的既有 API 资源 |
| 资源 | VM 多选、批量增删关联、可用/不可用数量及原因、组内优先级；已有 API 地址作为可选供给类型 |
| 模型 | 可用模型列表、公开模型名、已支持的映射；模型目录与真实可执行范围保持交集 |
| 计价 | 复用模型计价，设置分组倍率、用户组专属倍率；管理侧展示计价依据和版本，用户只看售卖价格 |
| 限额 | 用户总 RPM、用户在当前分组 RPM、Key RPM 三层同时检查；专属 RPM 仅替代分组默认值，0 不限制对应层；上游 VM 限额不被商业额度覆盖 |
| 付费方式 | 余额计费与订阅套餐；订阅具备起止时间、日/周/月额度与明确的窗口时区 |
| 复制与编辑 | 参考定制 sub2api 的分组复制、选择是否复制资源关联、模型规则校验；复制不携带用户授权、余额或秘密凭证 |
| 故障策略 | 第一阶段只在组内切换；后续显式备用分组可借容量，保留原计费分组及权限，限制环路与重试预算 |

第一版默认客户须经站长明确授权。公开组自动开放作为站长的显式政策，采用 sub2api 的公开/专属及 restrict_public_groups 语义，不把所有新组默认开放给历史用户。分组停用、授权撤销和模型收缩对下一次请求立即生效，粘性会话与已缓存候选也要复核。

### 4.2 统一现有三套范围

目标以 groups 与 group_resources 作为商业范围的唯一来源：group_resources 按 group_id、resource_kind、resource_id 关联资源，resource_kind 至少区分 vm 和 api_endpoint。增加该关联表的原因是：空槽可能没有上游 account_uuid、同一 VM 需要多组、现有 API 地址并不是 VM；现有 account_groups 与单池约束不能准确表达这些关系。

- 现有 groups 扩展为商业实体，保留历史 ID 及日志引用，不重写历史计价。
- vm_pools、vm_pool_members、Key 的 vm_pool_id / group_type / allowed_vms 先按第 12 节映射；迁移完成后退出客户 Key 授权链及 UI。
- account_groups 当前是上游账号关系，不能继续成为另一份可独立编辑的商业资源关联。核对所有读写方后，退出商业授权；若仍有独立账号统计用途，则明确为只读投影并给出删除条件。
- owner_user_id / origin 保留迁移和来源证据；新商业调用不由它授予资源。既有私人 VM 迁移时保持私有范围，不能自动公开。
- 未分组 VM 不进入客户商业调度；管理员测试仍走受控的诊断入口并记录为平台测试流量。

### 5.2 分配与解除关联语义

- 单 VM 编辑提交完整 group_ids，使用关系版本校验，原子替换；已有分组预选，搜索后不会丢掉未显示的勾选项。
- 同一 VM 可加入多个兼容组。停用组保留可见关联并标注停用；不能让普通客户调用停用组。
- 批量操作明确分为“添加到分组”“从分组移除”“替换分组”；不同操作不共用一个模糊的覆盖开关。
- 保存前校验全部 VM、分组、平台和操作者权限，冲突整批失败；返回关联增减摘要，记录操作人、原因、前后值及请求标识。
- 移除后新请求及下一轮会话不再选到该 VM；已开始的请求按原生命周期完成、正常结算。只有显式停机/撤权终止策略才中断在途请求。
- 多组关联只改业务关系，不重建容器、不重新绑定代理、不重置窗口或凭证。
- 清空关联显示“未分组，不接收客户请求”，不能自动落入无限制公共池。
- 反向在分组详情管理 VM 时调用同一个关系服务，避免双份成员列表。

### 5.3 代码与接口落点

现有入口包括 vm-action-menu.tsx、vm-detail-card.tsx、vm-owner-admin-card.tsx、vm-actions-provider.tsx、vm-actions-context.ts、vm-assign-owner-dialog.tsx、vm-owner.ts、vm-owner-line.tsx、detail-ops-tab.tsx 及对应测试。实施时替换属主操作链、列表列、类型和缓存刷新，而不是只给旧 owner 接口换文案。

规划新增 PUT /api/panel/vms/:id/groups，body 包含 group_ids、expected_version；批量关系操作使用 POST /api/panel/vms/groups/batch，显式 operation=add/remove/replace。VM 列表与详情响应增加安全的 groups 摘要和关系版本。

旧 PATCH /api/panel/vms/:id/owner 以及“收回进平台池”入口在迁移完成后退出运营路径。旧租户数据先有明确迁移结果，才移除失效代码；不得直接清空 owner_user_id 来伪装完成。历史迁移文件不改写。

## 6. 用户、API Key 与资金权益

### 6.1 用户管理

在既有 #/users 内扩展，而不是另建第二套客户表。列表参考定制 UsersView：状态、余额、已消费、授权分组、套餐、当前/上限并发、最近活跃；详情含基本资料、分组授权、专属倍率、Key 列表、用量跳转、资金流水和操作审计。

站长可创建/停用客户、调整并发/RPM、授权分组、充值/扣款、授予/暂停套餐。财务写入必须有金额、原因、操作者和幂等标识；同一请求重试不重复入账。停用账号后 Key 准入失效，会话、SSE 和多步操作按统一策略复核。

### 6.2 API Key

- 客户的 #/keys 默认列出本人全部 Key；创建时选择自己获授权的分组，显示该组模型、价格和当前权益。
- 支持名称、启停、期限、轮换、撤销、IP 规则、Key 自设额度、5h/1d/7d 窗口；用户级并发和商业上限始终有效。
- owner user_id 来自认证身份；group_id 在创建、编辑、使用三个时点校验。客户无法提交任意 user_id、用户余额、内部资源 ID 或管理员限定字段。
- 重置 Key 自设计数只影响 Key 保护阈值，不返还充值金额，不重置套餐消耗；若财务字段被管理员锁定，客户不能放宽。
- 创建新 Key、换 Key、换组都不绕过同一用户钱包与用户级限额；不跨 Key 复制消费权益。
- 已有 Key 的明文恢复/轮换契约按项目现状保留，经权限和审计保护；不在普通列表或导出中附带秘密值。
- 当前 #/keys 内嵌的 VmPoolsCard 迁至分组资源管理后退出，客户不再请求 VM 列表来创建 Key。

### 6.3 四种额度必须区分

| 层级 | 含义 | 控制方 |
| --- | --- | --- |
| 用户余额 | 全部 Key 共用的付费金额 | 站长或经验证的充值流程 |
| 用户套餐/商业额度 | 用户在某组的有效期与日/周/月权益 | 站长与订阅规则 |
| Key 自设额度 | 某把 Key 的额外消费保护 | 客户可收紧；不能突破上两层 |
| VM 上游额度 | 供应商的 5h/7d、Fable、并发、席位等真实限制 | 既有额度采样与调度模块 |

客户余额为 0 表示不能继续按余额消费；某项限制配置为 0 表示“不再增加这一项限制”时，UI 和接口必须明确，不能把它解释为无限资金。

### 6.4 结算契约

复用当前 pricing 与 usage 归一化，新增统一结算服务，覆盖 VM 与 API 两条推理路径。资金使用整数最小单位或固定精度类型，价格计算采用可审计精度；旧 REAL 余额迁移时生成差异报告，不能靠不同调用方各自浮点相减。

准入先检查用户、Key、分组、模型和资金，必要预留同一用户的在途额度；请求结束按真实 usage 与请求时价格快照结算，原子更新余额/套餐、Key 消耗、使用记录的结算状态和资金流水。并发流式请求不能只检查“余额大于零”后无上限放行；预留估算要有明确输出上限、未计价处理和受控超额政策，不能承诺仅靠最终 usage 就绝对零超支。

结算状态区分 pending、settled、free、unmetered、pending_pricing 等必要状态。缺价格或缺 usage 显示待处理，不能写 0 冒充免费。付费分组发布前检查模型定价；未知实际用量进入对账，不能凭空补 token。流式断开或失败若已有可信实际消耗，按公开计费规则结算；未发往上游的准入失败不扣费。重试尝试与用户请求分别记录，用户只承担当次策略确定的一份结算，内部重试成本不得无意重复扣给客户。

充值/扣款与请求结算均具备幂等键和事务。资金流水追加记录，冲正引用原流水；不通过修改历史明细实现退款。处理未知状态不能无条件释放预留后重复收费。价格修改、分组迁移、账号替换均不改历史实扣。

### 8.2 从当前定制 sub2api 明确吸收的页面行为

- GroupsView：平台/状态筛选、公开/专属、倍率、资源数量、复制分组、模型配置与可写字段授权。
- AccountsView：分组标签、平台/状态筛选、批量编辑、并发、优先级、今日账号统计与客户扣费分列、用量窗口。VM 的调度等级不直接等同于 sub2api 数值优先级，沿用各自已核实的排序语义后映射。
- UsersView：余额调整及历史、分组、用户专属倍率、并发/额度、Key 入口、用户用量联动、列可见性和分页。
- 管理 UsageView：统一日期与筛选条件，明细/错误/用户排行/Key 排行；Key 排行显示所属用户；成本与导出按独立权限。
- 用户 UsageView：本人全部 Key，明细/Key 排行/错误，同类布局；不展示多余用户列，不返回 account_cost、上游账号及内部模型映射。
- 两侧使用记录：模型/分组/入口分布、趋势、筛选下钻、取消旧请求、有界导出和取消导出；汇总不能阻塞明细首屏，未完成结果不能冒充 0。
- Ops：客户输入/余额/并发拒绝与服务故障分开，账号健康与站点 SLA 分开；内部重试尝试、队列、TTFT 与最终用户结果可关联但不重复计数。

不照搬当前 tapmodels 未支持的媒体平台、供应商两级结算、返利、支付供应商或 BPS/Excel 专属链路。它们属于 sub2api 独立能力，不由新增“分组”自动进入本次范围。定制 sub2api 刚加入的遥测、风控、提示词和重试功能，只参考明确有缺口的业务行为；tapmodels 已有实现保持单一来源。

## 9. 一次请求的完整执行契约

1. 验证协议 Key 和所属客户，处理禁用、过期、IP 规则；客户可控 header 不得注入内部用户/分组身份。
2. 解析 Key 的商业分组与用户授权/订阅，固定 billing_group_id、价格版本和计费方式；校验模型和协议权限。
3. 校验用户/分组/Key 限流、并发、钱包/套餐与在途预留；准入失败不消费上游资源。
4. 由分组关系生成允许的 VM / API 资源集合；为空或停用直接返回明确不可用，不能回退到全部平台池。
5. 把允许集合交给既有 PoolScheduler 或 ApiScheduler。继续使用 VM 额度、席位、工作时段、代理健康、熔断、冷却和现有公平/粘性策略；不另建商业调度器。
6. 粘性命中、排队取出、重试和备用组切换都重新检查资源资格；隔离键至少包含客户、Key、计费组与原有会话身份，服务端不跨客户共享可恢复会话。
7. 经过原 worker/kernel、原生客户端或 api-kernel 执行，保留原协议、流式语义和不可重放边界。
8. 收集归一化实际 usage、实际账号/VM、调度组和尝试结果；客户实扣仍使用步骤 2 固定的计费组。换资源不偷偷换价。
9. 统一结算服务完成一次原子账务提交，更新客户权益、Key 使用量和 usage_logs 结算状态；结束路径释放真实并发与预留。失败交给可恢复对账，不能 catch 后静默丢账。
10. 使用记录、统计、财务与 Ops 消费同一结算/请求事实的各自投影；凭证、原始提示词和上游秘密按权限及留存策略处理。

平台测试、健康检查、定时测试要明确 source 和 billable，不能因为使用 Master Key 就混进客户付费记录；产生的真实上游成本仍可进入运维资源统计。/v1/models、/v1/usage、各正式推理协议和管理测试都列入授权/结算覆盖清单。

## 10. 使用记录、账务与运维的口径

### 10.1 客户归属

新记录以请求发生时固定的 authenticated user_id、api_key_id、Key 名称快照、billing_group_id、价格快照归属。VM 重新分组、凭证更换、用户改名、Key 轮换/删除不能改变历史归属。

现有 ownerPred 的 user_id OR 当前 Key 所有人 OR vm_owner_user_id 不能直接沿用为商业客户授权。新客户查询只认调用用户快照；历史缺失 user_id 的记录只按可证明的既有证据回填，无法证明者保持未归属且仅管理侧可查，不能按当前资源归属猜测。

列表、详情、统计、模型分布、Key 排行、筛选候选、导出和账单钻取统一此规则。用户伪造 user_id、Key、VM、请求 ID 时不能扩大范围，响应字段同样要裁剪。

### 10.2 金额与 Token

| 指标 | 用途与约束 |
| --- | --- |
| 归一化 Token | 复用现有 disjoint input/cache 处理；输入、输出、缓存读、缓存写不可重复计数 |
| 标准计价 total_cost | 当前计价基准，保留价格版本；不直接称“供应商实际成本” |
| 客户实扣 actual_cost | 用户钱包/套餐实际消费，与结算流水一致；用户侧默认采用此口径 |
| 上游账号统计成本 | 根据账号计价规则或可信上游证据记录；与客户倍率独立，零成本与未知成本区分 |
| 采购成本 / 利润 | 只有存在可信采购成本口径时计算；订阅包月分摊和官方价估算明确标注，不能伪装成真实利润 |

价格快照保存分组倍率、用户组倍率的优先级和最终生效值；不把替代倍率误乘两次。后续高峰/模型专项价格纳入同一计算器。用户报表按约定时区和明确日界查询，数据库存储时间保持统一，滚动窗口不能误当自然日。

### 10.3 运维监控

#/ops 包含站点健康、成功率、TTFT、吞吐、队列、用户/Key/VM 并发、账号/出口异常、工作任务、告警与调度诊断。复用 overview、request_attempts、error-class、健康采样及 SSE；高频指标走已有内存/采样，不对每个轮询扫描全量日志。

分类先区分用户最终结果、每次上游尝试和运行健康：本地余额不足/输入错误不处罚 VM；明确资源池耗尽属于平台供给问题；客户取消、内容拒绝、上游鉴权失败各按明确分类处理。HTTP 200 内的流式失败不能算成功；没有样本显示“无数据”。不硬搬 sub2api Redis、WS 或 Go 运行时指标到当前没有对应组件的 tapmodels。

## 12. 迁移、清理与回退

1. 先做只读盘点：平台/管理员分配/用户自建 VM，所有 Key 的 owner/价格组/平台范围/allowlist/pool，用户余额、历史 user_id 缺失、现有 API 地址、外部面板调用方；生成逐项迁移预览，不接触生产数据。
2. 新增版本化迁移，不修改已应用 SQL。备份 SQLite、VM JSON、凭证/密钥相关配置；本轮规划不执行备份恢复或改密钥。
3. 建立确定的旧池/范围到商业组映射。相同资源范围但不同价格规则不可直接合并；旧 all Key 要记录原有效范围以及是否包含 API 地址，未解决映射不能默认给全部资源。
4. 既有私人 VM 和管理员分配 VM先转为该客户独享的资源组，或保留不对商业客户开放的待迁移资源；开放共享必须有明确的管理迁移决定。客户不再需要 VM 管理权限。保留原 owner/origin 作来源证据，不靠清空 owner 获得共享。
5. 旧上游 account_groups 绑定不足以涵盖空槽；以 vm.id 建资源关系。凭证改变不丢分组，原 account_id 的历史记录不改。旧 pool 动态成员变更与开放中的旧管理客户端要有明确停写切换点。
6. 旧 Key 的字面值、HMAC/加密和调用协议保持；映射 group_id、用户和限额并出差异报告。未归属 Key 由站长明确认领为客户或平台服务 Key，不能隐式得到无限商业额度。
7. 资金开账单独确认：已有余额/未收费 Key 限额不能互相当作已收款金额，不能凭空赠送或追扣历史消费。余额 0 的收费切换影响需在预览中列清并由运营安排充值/权益。
8. 在复制的数据库与 VM 元数据上执行影子授权、计价与报表比对，影子流程只比较不真实扣款。清空未知迁移项、处理旧请求并发后，短暂收口写入，原子切换新准入与结算，避免两套同时扣费。
9. 同次退出旧租户分配 UI、owner 编辑入口、客户 VM/代理操作、自建配额新建表单、VmPoolsCard 与旧 Key 资源授权逻辑。历史迁移/来源元数据和仍有明确独立消费者的字段有依据保留，列明读者与退出条件，不永久保留两套商业分组。
10. 客户历史记录以可信调用人回填；无证据者保持管理可见的未归属状态。报表不因 VM 迁移或 Key 删除把历史请求转给别人。
11. 计费切换前可回退代码与迁移副本；切换后已有真实充值/扣款，不能恢复旧库丢掉交易。应暂停新准入、保留事实与流水、完成在途结算，再修复或以可审计冲正恢复。迁移版本前进修正，不篡改历史 SQL 校验和。

## 13. 分阶段实施与完成条件

| 阶段 | 工作包与依赖 | 可评审产物 | 完成标准 |
| --- | --- | --- | --- |
| P0 基线和权限封口 | 固定迁移清单；客户字段白名单；核验代理导入附带绑定、Key owner 可写、日志归属范围 | 安全边界说明、最小回归和迁移预览 | 无客户越权入口；不调整生产资源归属 |
| P1 分组与 VM | groups、group_resources、分组页面、截图所有入口、多组批量管理；复用现有 VM/API 调度资格 | 可实际分配空槽与已有 VM 的完整功能 | VM 多组关系一致；未分组不服务客户；组内候选和共享容量正确 |
| P2 用户与 Key | 用户授权、组价格、客户 Key、登录落地与角色能力；依赖 P1 | 站长开户授权、客户建 Key 并请求 | 无 VM 所有权依赖；无跨组、跨用户绕过；模型目录一致 |
| P3 钱包与结算 | 管理员余额转账、预留、幂等账务、价格快照、VM/API 两路径、恢复对账 | 真实业务链“管理员余额→用户充值→创建 Key→请求→扣费→流水” | 并发、流式、取消、重复事件和重启恢复通过，未知不假零 |
| P4 使用记录与 Ops | 定制 sub2api 用量布局、排行/导出/安全 DTO，站点运维、告警/轨迹；依赖 P2/P3 可与页面工作并行 | 站长全站、用户全部 Key、运维诊断和账务联动 | 各表口径一致，隔离有效，导出有界，指标分类可信 |
| P5 套餐与进阶分组 | 用户组套餐日/周/月窗口、专属倍率、显式备用组；复用同一钱包/记录链 | 余额/订阅两种清晰售卖方式 | 不双扣，过期/撤销立即生效，备用组保持原计费与权限 |
| P6 升级与退出旧逻辑 | 演练迁移/回退、删除失效入口/读写/文案/测试、更新指南 | 可复核迁移报告与发布说明 | 私有数据不公开，历史不串户，资金不丢账，旧路径无绕过 |

P1 的 VM 分组是首个可见交付，但不能在 P3/P4 完成前把整个系统称为可商业运营。线上支付、退款供应商、返利、供应商门户、复杂复合组和当前不支持的新平台另立范围；不是本轮核心运营闭环的先决条件。

## 14. 验收矩阵

| 场景 | 关键验收结果 |
| --- | --- |
| 空槽分组 | 未绑定凭证的 vm-01 可加入多个组，但可用候选数不增加 |
| 三个截图入口与表格 | 卡片、弹窗、运维区、分组列、编辑多选读写一致；保存后同步刷新 |
| 批量 add/remove/replace | 操作语义明确，平台/权限校验整体一致，冲突无部分更新 |
| 多组共享 VM | 不复制席位和上游额度；移出一个组不影响其他组的合法关联 |
| 未分组/空组/停用组 | 客户不可调用，不隐式退回全局池；平台诊断单独标记 |
| 撤权及粘性 | 已撤销资格不因旧 session/缓存/排队/重试绕过；在途结束策略明确 |
| VM 与 API 两种后端 | 同一分组授权、钱包和计价规则；API 地址路径无旁路 |
| Key 修改 | 客户提交 user_id、其他组、VM ID、平台限额均被拒绝或按白名单剔除；不能转移 Key |
| 代理 import 附带绑定 | 目标资源权限明确；客户旧路径不能绑定他人的 VM |
| 余额与多 Key | 两把 Key 共享资金，在途预留原子计算；更换/重置 Key 不恢复余额 |
| 幂等充值/结算 | 重复按钮、重试、回调和恢复只记一次；流水与余额一致 |
| 失败/取消/部分流 | 无上游执行不扣费，已有可信 usage 按规则记账，未知待处理，不重复扣重试 |
| 分组价与账号成本 | 两者独立；组价格变化和备用组不改变既有请求快照 |
| 用户记录 | 默认本人全部 Key；旧 Key 删除、VM 换组、用户改名后仍正确归属 |
| 响应裁剪 | 列表/详情/筛选/排行/导出均无其他用户、上游秘密、成本和未授权正文 |
| 统计与资金 | 相同过滤条件下 actual_cost、结算流水和消费汇总可对账；充值不算请求收入 |
| Ops / SLA | 客户错误不误罚 VM，池耗尽及流式逻辑失败可诊断，无样本不冒充成功 |
| 套餐 | 开始/到期、时区日界、额度重置、撤销及余额回退策略可验证，不自动双扣 |
| 升级 | 生产副本演练前后授权差异可列举；私有 VM 未共享、历史未串户、资金未重算 |
| 路由与缓存 | /cc 和 /console 下 Hash 深链接可刷新；不同角色切换清空敏感数据，用户不落入内部总览 |

测试按现有 Node 单元/E2E、Vitest 与必要 Go 路径分层；财务使用真实临时 SQLite 事务测试，不能全靠 mock；接口角色矩阵与截图位置的组件/浏览器验证都要覆盖。测试性能只记录实测结果，不在规划里承诺未经测量的吞吐。

## 15. 可选拓扑：直接使用现有 sub2api 作为运营入口

如果最终要求“所有用户直接登录已经运行的 sub2api”，可以让 sub2api 负责用户、分组、Key、价格、钱包、使用记录及 Ops，把 tapmodels 作为受控供给执行端。此时只保留一个客户账本，tapmodels 侧记录上游资源消耗而不再向同一客户扣款。

但这条路需要先定义可验证的服务间授权、允许资源范围、真实 usage、请求标识、错误分类和健康反馈契约。把整个 tapmodels 简单登记成一个上游 API 账号，无法自动获得逐 VM 分组、5h/7d 状态、单 VM 管理与选择；如果需要这些功能，就必须实现资源映射及控制接口。服务凭据不得交给客户，也不能让客户伪造分组/VM pin。

本轮依用户“按 tapmodels 规则规划”和 VM 页面改造要求，采用前述 tapmodels 内部整合主线。此替代方案仅用于明确部署边界，不在同一实施中同时建设两套运营系统。
